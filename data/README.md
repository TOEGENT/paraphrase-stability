# Data specification

## Назначение

Каталог хранит описание источников, версий и схемы датасета для оценки устойчивости ответов SLM к семантически эквивалентным преобразованиям вопроса.

## Обязательная схема записи (уровень варианта)

Каждая запись (JSONL) должна включать минимум:

- `task_id` — идентификатор исходной задачи.
- `variant_id` — идентификатор варианта преобразования.
- `question_original` — текст исходного вопроса.
- `question_transformed` — текст преобразованного вопроса.
- `transformation_type` — тип преобразования.
- `model_answer` — ответ фиксированной SLM на `question_transformed`.
- `equivalence_status` — статус эквивалентности ответа относительно исходного ответа (`equivalent`, `non_equivalent`, `unclear`, `insufficient_context`).
- `k` — число эквивалентных ответов среди проверенных вариантов текущего `task_id`.
- `N` — число проверенных вариантов текущего `task_id`.
- `split` — сплит (`train`, `val`, `test`).
- `model_version_id` — версия/идентификатор SLM.
- `protocol_version_id` — версия протокола аннотации/оценки.

## Правила разделения

1. Все варианты одной задачи (`task_id`) должны попадать в один и тот же `split`.
2. Итоговый `test` используется только после фиксации метода.
3. Статусы `unclear` и `insufficient_context` не должны автоматически считаться `non_equivalent`.

## Происхождение и версии

- Для каждого MVP-релиза публикуются:
  - версия источника задач;
  - версия генератора преобразований/промптов;
  - `model_version_id`;
  - `protocol_version_id`.
- Формат версий рекомендуется фиксировать тегами вида `dataset-mvp-wN`.
