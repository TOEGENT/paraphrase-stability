# Один человек и один ИИ-агент: MVP за рабочий день

Один исследователь ставит задачу ИИ-агенту, предоставляет разрешённые входы и проверяет результат; агент последовательно выполняет сбор данных, разметку, обучение, оценку, обновление статьи и самопроверку. Рабочий цикл описан для одного дня продолжительностью около восьми часов. Каждый выпуск получает `mvp_id` и каталог с манифестом, данными, моделью, оценкой, черновиком статьи, замечаниями и списком ограничений. Контракты файлов находятся в [pipeline_contracts.md](pipeline_contracts.md).

## Порядок одного дня

| Время | Действие человека и агента | Проверяемый результат |
|---|---|---|
| 09:00–09:30 | Человек выбирает один измеримый результат дня и даёт агенту предыдущий MVP, замечания, конфигурацию, доступные источники и бюджет вычислений; агент проверяет входы и перечисляет блокеры | Задание дня, `previous_mvp_id`, конфигурация и план запуска в манифесте |
| 09:30–11:00 | Агент собирает или синтезирует небольшой набор новых задач, исправляет отмеченные вчера примеры, получает перефразы и ответы фиксированной SLM, проверяет схемы и происхождение | Кандидат датасета, журнал изменений и очередь сомнительной разметки |
| 11:00–12:00 | Агент проверяет эквивалентность вопросов и ответов, разрешённые случаи переводит в `k`, `N`, `k/N`, формирует разделение по исходной задаче; человек разбирает только спорные случаи, влияющие на выпуск | Версия данных с проверенными метками и исключениями |
| 12:00–14:00 | Агент извлекает признаки только из исходной пары, обучает постоянный базовый метод и минимальную MLP на `train`, проверяет на `val`, сохраняет обработку признаков и checkpoint | Воспроизводимая модель и отчёт обучения |
| 14:00–15:00 | Агент запускает оценку на `val`, пересчитывает метрики из сохранённых прогнозов, сравнивает с базовым методом и отмечает ошибки | Прогнозы, метрики, короткий отчёт и явные ограничения |
| 15:00–16:00 | Агент обновляет статью по **проверенным результатам текущего MVP**, указывает источники чисел, затем отдельным проходом проверяет её и весь запуск по инструкции рецензента | Черновик, таблица источников утверждений и замечания самопроверки |
| 16:00–17:00 | Человек проверяет выборку данных, команду воспроизведения, числа в отчёте и ключевые выводы; агент исправляет найденные ошибки и повторяет затронутые этапы | Протокол проверки и кандидат в выпуск |
| До конца дня | Человек принимает или отклоняет кандидат; агент сохраняет манифест, известные ограничения и следующую конкретную задачу в общем репозитории | Дневной MVP либо предыдущая проверенная версия с причиной задержки |

Временные окна ориентировочные: при задержке сначала сокращается размер выборки и глубина анализа, а статус результата сохраняется честно. Независимый `test` не используется для ежедневного подбора метода. Один и тот же агент может выполнить рецензентский проход, но это самопроверка; независимой рецензией её называть нельзя.

## Что реально можно сделать первым днём

Сейчас репозиторий содержит пять демонстрационных вопросов, примеры JSONL, инструкции, CLI для вызова трёх модельных ролей и незаполненную `configs/pilot.yaml`; сквозного исполнимого конвейера пока нет. Из этого за день разумно собрать **технический MVP**: одну команду на маленьком синтетическом наборе, валидацию контрактов, расчёт `k/N`, минимальное обучение и оценку, черновик и самопроверку с пометкой `demo`. Такой результат докажет, что этапы передают файлы друг другу, но не покажет качество предсказания на новых задачах.

Для **исследовательского MVP** нужно подготовить следующие входы или принять явные решения до запуска:

| Пробел | Почему мешает однодневному результату | Минимальное решение |
|---|---|---|
| Источник задач и права использования | Примеры из `data/examples/` демонстрационные и слишком малы для содержательной оценки | Выбрать доступный набор, зафиксировать источник и допустимое использование; для первого дня ограничить размер |
| Фиксированная SLM и вычислительный доступ | Без версии, способа запуска и ресурсов нельзя получить воспроизводимые ответы | Указать модель, системную инструкцию, greedy decoding, лимит ответа и доступный локальный или API-запуск |
| Генератор перефразов, оценщик и бюджет | Неясно, какими моделями создавать и проверять варианты и сколько вызовов допустимо | Выбрать провайдеры или локальные модели, лимит запросов и порядок ручной проверки `unclear` |
| Признаки для MLP | Нет выбранной модели эмбеддингов и способа её получения; архитектура описана, код отсутствует | Зафиксировать доступный эмбеддер либо объявить простые числовые признаки только для `demo` |
| Конфигурация и запуск | В `configs/pilot.yaml` есть `UNSET`, CLI модельных ролей уже работает отдельно, а зависимости и команды сквозного обучения не объявлены | Заполнить отдельную конфигурацию дня, добавить зависимости, реализовать одну точку запуска и короткую проверку результатов |
| Объём и разделение данных | Пять примеров не дают надёжных `train`/`val` и сравнения MLP с базовым методом | Задать минимальный объём и split по `question_id`; при меньшем объёме выпускать только технический `demo` |

**Критерий готовности дня:** одна документированная команда повторяет запуск, манифест связывает все артефакты и версии, метрики пересчитываются из прогнозов, а текст не заявляет больше, чем показали данные. Если один из обязательных входов исследовательского MVP отсутствует, агент выполняет доступный технический сценарий, фиксирует блокер и оставляет следующую конкретную задачу; молчаливой подмены реальной модели или данных заглушками нет.
